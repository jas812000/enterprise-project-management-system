# EPMS Local Quality Gate — Reporting Engine

## 1. Overview

The `reporting/` directory contains the Python reporting engine for the EPMS Local Quality Gate (BN1).

The reporting engine processes the XML results generated by Checkstyle, PMD, and SpotBugs and combines them into a unified HTML quality report.

Its purpose is to provide developers with a consolidated view of code-quality findings, scanner execution results, and overall quality-gate status.

The reporting engine is invoked by the main quality-gate runner.

## 3. Reporting Components

| Component | Responsibility |
|---|---|
| `generate_report.py` | Coordinates report generation |
| `report_parsers.py` | Processes scanner XML results |
| `report_html.py` | Provides HTML report-generation functionality |
| `open_report.py` | Opens the generated report in a browser |
| `render_report/` | Contains modular HTML rendering components |

The rendering modules separate report layout, styling, controls, and presentation logic.

This organization supports maintenance and future reporting improvements without requiring all HTML-generation logic to reside in one Python file.

## 4. Report Generation Workflow

The reporting engine receives the results produced by the scanner wrappers.

```text
Checkstyle
    |
    +-- checkstyle.xml
    |
PMD
    |
    +-- pmd.xml
    |
SpotBugs
    |
    +-- spotbugs.xml
    |
    v
report_parsers.py
    |
    v
Parsed scanner results
    |
    v
generate_report.py
    |
    v
HTML rendering components
    |
    v
local-report.html
    |
    v
Timestamped ZIP archive
```

The main quality-gate runner coordinates scanner execution, reporting, and artifact packaging.

## 5. Generated Artifacts

The primary HTML report is generated at:

`quality/Local_Scans/reports/work/local-report.html`

Raw scanner XML reports are stored in the same working directory:

```text
quality/Local_Scans/reports/work/
├── checkstyle.xml
├── pmd.xml
├── spotbugs.xml
└── local-report.html
```

The main runner also creates a timestamped ZIP archive in:

`quality/Local_Scans/reports/`

Example filename:

`local-quality-report-YYYY-MM-DD-HHMMSS.zip`

The timestamp distinguishes individual report archives.

All generated reports are excluded from Git.

## 6. HTML Report Features

The consolidated HTML report provides:

- Overall quality-gate status.
- Individual scanner results.
- Counts of detected findings.
- Severity classifications.
- Source file and location information when available.
- Interactive controls for reviewing findings.
- A consolidated view of Checkstyle, PMD, and SpotBugs results.

The report supports the following severity categories:

| Severity | General Meaning |
|---|---|
| Critical | Highest-priority findings |
| High | Significant findings |
| Medium | Moderate findings |
| Low | Lower-priority findings |
| Info | Informational findings |

Severity classifications are mapped from scanner-specific metadata.

Not every scanner necessarily produces findings in all five categories.

## 7. Running the Reporting Workflow

The supported way to generate the report is through the main BN1 runner.

From the EPMS `backend/` directory:

```bash
sh ../quality/Local_Scans/run-local-checks.sh
```

The runner:

1. Executes Checkstyle.
2. Executes PMD.
3. Executes SpotBugs.
4. Collects scanner results.
5. Generates the consolidated HTML report.
6. Creates a timestamped ZIP archive.
7. Opens the HTML report in the browser.

The reporting scripts are internal components of this workflow.

Developers should use the main runner rather than invoking individual reporting modules without their required arguments.

## 8. Error Handling

The quality gate distinguishes between detected code-quality violations and scanner execution errors.

| Exit Code | Meaning |
|---|---|
| `0` | Quality gate passed |
| `1` | Quality violations detected |
| `2` | Scanner execution or reporting error |

The report provides visibility into scanner results, while the main runner determines the overall exit status.

A scanner execution failure must not be treated as a successful quality check.

## 9. Python Requirements

The reporting engine requires Python 3.10 or later.

Python is used for:

- XML parsing.
- Scanner-result processing.
- HTML report generation.
- Report presentation utilities.

The reporting engine uses modular Python files maintained within the EPMS repository.
